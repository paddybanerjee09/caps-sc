`src/recovery/useRecoveryDay.ts` checks date/timezone at open, foreground and every 15 seconds while mounted. Recovery always uses the current device calendar day rather than the Today timeline's selected historical date. A midnight change creates a fresh completion indicator; no historical response is deleted. Open historical forms retain their original day and timezone. Clock controls explicitly show device timezone and original recovery-day assignment, preserve instants, reject nonexistent DST clock times and expose the alternate occurrence of a repeated local clock time.

## SQLite v10: relational map and lifecycle

CAPS still has one device-local athlete and no authenticated backend. The owner ID is the explicit literal `device-local`; it is not a login, account token or multi-user security boundary. Every new repository query binds that owner. An authenticated athlete/server/RLS implementation must be designed before multi-athlete remote sync. No backend migration or remote sync was invented.

| Table | Key / relation | Stored purpose |
| --- | --- | --- |
| `recovery_owner` | PK `id`, constrained to `device-local` | Parent row for the current local athlete's Recovery data. |
| `daily_questionnaires` | PK `(owner_id, local_date)`; owner FK | Exactly one active response per waking local date. Columns retain timezone, status, revision, completion/update timestamps and `response_json` containing original full sleep instants, null/unanswered or true-zero ratings, awakenings, optional awake minutes and mood. |
| `questionnaire_revisions` | PK `(owner_id, local_date, revision)`; composite FK to active questionnaire, `ON DELETE CASCADE` | Each saved response version and recorded time. Editing increments revision rather than losing the previous inputs. Stale revisions are rejected so an older editor cannot overwrite a later save. |
| `health_measurements` | PK `(owner_id, platform, external_id, metric)`; owner FK; index on owner/day/acquisition | Idempotent native sample identity. Indexed date/time columns support history, while JSON retains value, canonical unit, source/device/app, subtype, protocol, quality, acquisition/ingestion/interval times, timezone and native metadata. One source sleep session can yield duration and efficiency with the same external ID but distinct metric keys. |
| `recovery_snapshots` | PK `(owner_id, local_date)`; owner FK | Reproducible daily cache: nullable SRI/ORI, algorithm versions, objective marker count and computation timestamp. `inputCount` describes objective marker types, not the six SRI inputs. |
| `metric_baselines` | PK `(owner_id, local_date, comparable_key)`; owner FK | Mean/sample SD/count/reference window/Z/CV for one metric/platform/source/subtype/protocol/unit identity. RMSSD baselines use lnRMSSD. |
| `health_connections` | PK `(owner_id, platform)`; owner FK | Connection/read capabilities, last successful sync, useful error and serialized native cursor. The cursor contains the minimal source sleep cache needed to recompute edits/deletions. |
| `recovery_preferences` | PK `owner_id`; owner FK | Per-metric source choices. Source selection triggers derived-data recalculation. |

Questionnaire save is a serialized transaction: validate original inputs and dates, check optimistic revision, upsert the active response, append its revision, recompute the affected day's snapshot, then commit. A draft has no SRI even if some scoring fields are filled. A completed response needs all six scoring inputs plus valid sleep dates; optional mood is excluded from SRI. Resaving a completed day as a draft deliberately clears its current completion/score until resubmission. The history UI permits editing prior days and those changes flow to Progress.

Health batch save is another serialized transaction: validate every normalized sample, reconcile explicit upstream deletions (or a fully read bounded replacement window), upsert stable sample keys, persist the corresponding connection/cursor, rebuild affected derived records, then commit. A disk failure rolls back both samples and cursor. A partially failed native category retains its old anchor/observations; successful categories can advance atomically. Failed import does not replace missing values with zero. The current implementation rebuilds health-derived snapshots/baselines after health/source changes; maps and 28 calendar-slot lookups avoid a full-history scan for every daily baseline. Native sleep normalization still needs long-history device profiling.

There is **no second weight database**. `listWeights` joins `weight_logs.timeline_entry_id` to `timeline_entries.id`, reads canonical kg and applies the existing weight conversion helper for display. These legacy weight rows have no captured acquisition timezone; their chart date follows current device timezone like existing Home. Existing `sleep_schedules` and planned timeline windows are not imported as observed asleep time.

The initializer adds idempotent v10 DDL and a `daily_questionnaires` sentinel while preserving all previous nutrition/strength/skill repair paths. Existing regression fixtures now expect version 10. The migration is additive; it does not drop or rewrite old weight, sleep, training or meal data. Reinstalling an older binary does not undo these tables. Do not lower `user_version` or drop Recovery tables/revisions as an untested rollback; back up the database first. Explicit imported-health deletion waits for ongoing sync, disconnects, removes samples/cursors/raw sleep cache and rebuilds derived caches, retaining questionnaire revisions and existing weight logs. Disconnect alone retains data and does not revoke platform permissions.

## Calculations and chart decisions

- `sri_v1`: six equal higher-is-better contributions, awakenings capped at five **only in scoring**, rounded to 0–100. Input awakenings have no artificial upper slider limit. These are app choices, not validated cutoffs; it is not Hooper or percent recovered.
- Objective baselines: preceding 28 calendar days, excluding the plotted/current day, at least 14 distinct valid comparable days for Z; zero SD or nonfinite arithmetic suppresses Z. One latest eligible observation per comparable date. Raw SDNN and RMSSD never merge; RMSSD's baseline is logarithmic and labeled accordingly. No assumption that higher HRV means better recovery.
- Health readings retain their original assigned day/timezone, including a supplied fixed acquisition UTC offset where an IANA zone is absent; sleep uses the wake-ending source zone/session boundary. Historical/stale values are explicitly dated and never used as today's missing marker. The temperature/HRR cards remain unavailable because no comparable deviation or standardized HRR test pipeline is present.
- Manual sleep interval is not asleep duration. Optional reported awake minutes are required to derive estimated/manual asleep time; no questionnaire sleep efficiency is invented. Native efficiency requires actual compatible in-bed coverage.
- ORI returns null in calculations, persisted snapshots and chart series. The experimental label and absent-model explanation remain visible; no weights or transforms were invented.
- Daily weight uses the latest eligible existing weigh-in. Its average uses the trailing seven calendar days with at least four observed days, reports partial coverage, and never replaces the daily gaps.
- Charts use existing `react-native-svg` behind feature components rather than adding a second rendering library. Five categories have meaningful separate scales; HRV subtype/source/protocol/model identities remain separate series. Legends stay at card tops and retain toggles across timeframe/group changes while Home remains mounted.
- Week is Monday–Sunday, Month uses actual calendar length, Year shows Jan–Dec monthly means. Lifetime is daily through 120 days, monthly through eight years, annual thereafter. Period means use valid comparable daily values; missing days are not zero and incompatible source/formula buckets suppress a mean. Tooltips expose method, observations/eligible days/coverage, source, time and version.

## Verification and release limits

Passed: `npm run typecheck`, full `npm run lint`, `verify:nutrition`, `verify:conditioning`, `verify:strength`, `verify:skill`, `verify:recovery`, `verify:recovery-input`, `verify:health`, `verify:progress`; dependency compatibility and Expo native configuration introspection. Android and iOS Metro/Hermes exports passed with the local native compiler permitted outside the sandbox (1358/1435 modules). These are JavaScript bundle checks, not signed native builds or device proof.

Before release follow the unrun physical-device procedure in `recovery-native-setup.md`, set actual bundle/package identifiers, integrate the Android permission-rationale/privacy-policy destination, establish retention/security policy, and profile long histories. SQL uses the app sandbox/platform device protection; database-level encryption and authenticated cloud sync are absent. Optional device notifications and ORI calibration remain future work. No raw health data is sent to analytics or logs by this implementation.
