# Conditioning Records

Status at `e492e06` · SQLite model and local repository implemented. See [[Conditioning]], [[Conditioning Execution]], and [[Data and Persistence]].

- `src/data/conditioningMigration.ts` is migration 7 in `src/data/database.ts` for `caps.db` (`3f111e1`). `conditioning_owner` supplies a device-local owner. `conditioning_templates` and ordered `conditioning_template_stations` store reusable prescriptions. `conditioning_sessions` owns snapshots and may reference a source template and a Home `timeline_entries` row. Both references use `ON DELETE SET NULL`. Session children use `ON DELETE CASCADE` and store segments, location points, occurrences, splits, upload jobs, and runner state.
- `src/data/conditioningRepository.ts` serializes domain writes through `enqueueConditioningWrite` and groups template/session and timeline updates in transactions. `planConditioningSession`, `updatePlannedConditioningSession`, `startConditioningSession`, `finishConditioningSession`, `saveConditioningSession`, and `logConditioningSession` are the principal transitions. A separately authorized plan edit can replace its snapshot. Editing or archiving a source template never rewrites a plan or completed history. `logConditioningSession` and `saveConditioningSession` return existing terminal records for repeated saves on the same session.
- `src/conditioning/types.ts` and `status.ts` separate session state (`planned`, `in_progress`, `finished_draft`, `completed`, `ended_early`, `cancelled`) and sync state (`local_only`, `pending`, `uploading`, `synced`, `failed`). Time crossing a plan date leaves it planned. Start and Log can use a plan in place. Discard restores its date and planned status or deletes a new unplanned recording and its timeline entry. Cancellation keeps the cancelled session record, removes its timeline entry, and excludes it from the calendar query.
- Calendar queries use `YYYY-MM-DD`, favoring the recorded performed local date over the scheduled local date. Stored timezone metadata is IANA. `scheduledInstant` constructs the Home timestamp using device-local date and clock fields. `calendarDateForSession` relies on the persisted date so moving between timezones does not recategorize the month row. `bumpTimeline` and `workspace.bumpRevision` invalidate affected views after saves (`0772f4e`). Home uses absolute-time entries and `timelineCategories.conditioning.color`.
- Store seconds, meters, and kilograms. Convert display values with `src/conditioning/units.ts` using the in-memory `unitSettings` in `src/state/AppStateContext.tsx` (defaults to metric distance). Changing the setting leaves stored values intact. Target RPE and observed session RPE are independent. Blank observed RPE is `null`. Manual performed times must be at or before now, and snapshot validation caps work occurrences at 2,000 (`src/conditioning/validation.ts`).

## Upload status on main

Saving a completed/ended-early session creates a pending job. `src/data/conditioningSync.ts` (`091cc58`) defines an HTTP transport and a helper that upserts the session, skips already acknowledged point sequences, uploads remaining points in batches of 250, checks occurrence and split counts, then finalizes. The helper accepts an initial acknowledgement cursor, updates a local job copy, and returns the resulting job. Checkpoint persistence across a failed call needs an integration layer. Source search found no app caller for `syncConditioningBundle` or `createHttpTransport`, and the documented `EXPO_PUBLIC_CONDITIONING_API_URL` is absent from app source and `.env.example`. Treat pending jobs and the tested transport helper as local scaffolding. `docs/conditioning-implementation.md` implies setting the URL activates upload, which source inspection does not support.

`npm run verify:conditioning` passed during the backfill on Node v24.18.0. The script exercises the Node SQLite harness, owner scoping, snapshot retention, state transitions, and the mock transport. Device SQLite, native UI, and an actual upload service were outside that check.
