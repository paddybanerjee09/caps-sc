## Proposed first release

- Put `MonthlyTimelineComponent` first on the existing Strength tab. Have the parent supply `MonthEvent` rows from a Strength repository. Use the marker to show workout status and the selected day to open workout detail. Keep logged sessions on their recorded local date. Calendar scheduling can follow manual logging.
- **Create Workout** saves a named template containing ordered exercises and target sets. **Log Workout** offers **From Saved Workout** and **Blank Workout**. Selecting a template copies its targets into an editable draft. Completion saves only confirmed work, including substitutions or skipped sets. Use stack screens with the current CAPS card and input patterns. Preserve drafts while the athlete visits exercise search or the estimate detail.

## Catalog

- Recommend a pinned local snapshot of structured metadata from [Free Exercise DB](https://github.com/yuhonas/free-exercise-db), which lists more than 800 movements and publishes its [Unlicense](https://github.com/yuhonas/free-exercise-db/blob/main/LICENSE.md). Import a curated set of factual fields, track the source revision, allow custom exercises, and retain stable CAPS IDs with upstream IDs as provenance. Launch coverage and aliases still need checking for conventional lifts, unilateral variations, carries, jumps, throws, and isometrics. Free Exercise DB's maintainer [could not verify image provenance](https://github.com/yuhonas/free-exercise-db/issues/2). Keep imported photos and instructional text out of the initial seed.
- [wger](https://wger.readthedocs.io/en/latest/api/api.html) has a public exercise API with [Creative Commons terms listed per entry](https://github.com/wger-project/wger). [ExerciseDB.io](https://exercisedb.io/terms) is a paid option if in-app GIFs and taxonomy become a priority. Its terms govern the data and paired GIFs. The archived ExerciseDB adapter is historical evidence, with its endpoint outside the scope of this review.

## Proposed estimated strength emphasis

- Build a pure, versioned estimator over work sets. Use independent qualitative levels for maximal strength, hypertrophy, and power, plus explicit insufficient data. For each quality, return supporting sets, a short rationale, and missing inputs. Keep muscular endurance for a later version if repeated-effort and rest data justify it.
- Strength evidence is heavy exercise-specific relative load, preferably against a recent reference for the same lift. Hypertrophy evidence is multiple challenging work sets with a variety of workable rep ranges and optional set RIR (reps in reserve). Power evidence requires explicit explosive intent or velocity evidence, with a supported movement and suitable load context when applicable. A low rep count alone leaves power undetermined. Exclude warm-ups and skipped sets, preserve unknowns, and avoid aggregating raw tonnage across different exercises.
- Estimate both template target previews and performed sessions. The completed estimate uses actual work sets. Persist its version, coverage, evidence, and source with the session. Keep measured progress in longitudinal metrics such as same-lift rep or load PRs. The physiology references concern programming over weeks and inform heuristics for session emphasis. [ACSM position stand](https://pubmed.ncbi.nlm.nih.gov/41843416/) · [Resistance training network meta-analysis](https://pubmed.ncbi.nlm.nih.gov/37414459/) · [Proximity-to-failure meta-regressions](https://pubmed.ncbi.nlm.nih.gov/38970765/).

## Conditioning reference and follow-through

- `src/conditioning/emphasis.ts` applies the first matching RPE, duration, and session-wide rest-to-work profile per usable bout, then weights six independent indexes by work seconds. The top index is primary, with up to two secondary indexes at 40 or higher. Missing bouts can produce partial coverage. Without usable positive work or known total recovery, scores are null. All `heuristic-v0.1` outputs carry low confidence.
- `src/screens/conditioning/ConditioningAdaptationsScreen.tsx` builds previews from draft targets. For session routes it prefers stored `emphasisJson`; otherwise it uses the prescribed phase snapshot with session RPE as fallback for missing target RPE and labels it `actual`, including when reached from a planned session. `rg -n 'estimateEmphasis|emphasisJson' src` found no normal app save caller that supplies the estimate. This is an input provenance and persistence discrepancy to avoid in Strength.
