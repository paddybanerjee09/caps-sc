## 1. Build the domain, offline catalog, and SQLite repository

- Seed a curated, pinned snapshot of factual [Free Exercise DB](https://github.com/yuhonas/free-exercise-db) metadata. Keep stable CAPS IDs, source revision and upstream IDs, equipment, muscle groups, and aliases. Audit common lifts, bodyweight and assisted movements, carries, and power movements. Support user-defined exercises. The upstream [photo rights are unverified](https://github.com/yuhonas/free-exercise-db/issues/2). The initial catalog is text-only and searchable offline by name and alias.
- Add a forward migration in `src/data/database.ts` from the active schema. Model template header → ordered exercises → target sets and session header → ordered exercise snapshots → performed sets. Persist the logged title, start/end timestamps, local end date and timezone, optional source template ID, and versioned estimate. Retain history after catalog changes or template removal. Keep draft state in the Strength navigation workspace while opening child screens.
- Store kg and seconds and use existing unit settings at display and input boundaries. Define per-implement load, unilateral reps, bodyweight and assistance explicitly. An explicit bodyweight selection satisfies the required weight field. Require a trimmed title, at least one exercise, valid weight, positive integer sets and reps, and a valid end time. RPE, rest, and notes are optional. Retain the distinction between omitted rest and zero rest. Use the repeat-set fields as the default for each set and allow individual sets to be edited or skipped in a log.
- Save the session, work sets, estimate, Home timeline row, and any template create/update/archive in one transaction. Use a stable draft/session ID to make Save retry-safe. Failed writes keep the draft and any original template available. Publish timeline and Strength revisions after commit. For template-only creation, save the template independently.

## 2. Implement the Strength hub and workout screens

- Keep the existing `strength` tab and use the app's custom stack pattern. Put `src/components/MonthlyTimelineComponent.tsx` first on `StrengthTrainingScreen`, then **Log Workout**, **Create Workout**, and **Saved Workouts**. The selected day lists logged sessions with a route to read-only detail. Have the Strength parent supply `MonthEvent` rows. Use the saved local end date, including when a workout began the previous day or the device timezone changes.
- **Create Workout** opens the workout builder in template mode with title, exercise search, table, and an emphasis preview. Save the template without time fields or a history row. **Log Workout** opens the same builder in log mode with an empty table, a title field, and **Ends at** using `LogTimeChanger`. The hub's **Saved Workouts** dropdown lists every saved title. Also expose **From Saved Workout** within the log flow. Both saved entry points hydrate the same log builder with title and exercises, fresh end time, and **Save Workout** on.
- Put exercise search in the upper part of the builder, the workout table beneath it, and the calculated focus button beneath the table. Use React Native's existing `FlatList` for search. Give the results a deliberate bound or use one vertical virtualized list with header/footer content. Show a small initial result limit, search across the full catalog, and let the user load more matches. Keep the table and actions reachable even with many search results. Avoid nesting a vertical `FlatList` inside a vertical `ScrollView`.
- Tapping a result opens a dedicated exercise editor for **Weight\***, **Sets\***, **Reps\***, RPE, rest between sets, and notes. Use CAPS steppers/presets for numeric input. Saving updates the draft and returns with scroll/search state intact. Make table rows editable with columns in this order: Exercise, Weight\*, Sets\*, Reps\*, RPE, Rest, Notes. Keep the exercise names readable on small screens, with horizontal table scrolling or a narrow-screen layout that preserves the same reading order. Show mixed set values explicitly.
- Place **Cancel**, the **Save Workout** toggle, and **Log Workout** in a fixed, safe-area footer. A blank log starts with the toggle off. On commit, turning it on creates a reusable template from the draft. A saved workout starts with it on. Logging in that state updates the source template with the reviewed draft. Turning it off and successfully logging archives the source template. Explain that consequence beside the toggle. Toggling and cancelling leave storage untouched. Guard dirty drafts across Back, Cancel, and system Back.

### Time semantics

Capture the current time when a fresh or saved log opens. Pressing **Ends at** expands `LogTimeChanger` in place. Its full variant provides hour and minute controls. Show the date in the Strength wrapper and allow selecting a past date there so long backdates do not require repeated hourly steps. Use `maximumDate` and revalidate on commit to reject future timestamps. An explicitly chosen end time survives exercise edits and subnavigation. Show **Estimated duration** separately and derive start time from end minus duration. Store both timestamps and use the end date for the Strength month.

Use a deterministic first-pass duration model, proposed as 3 seconds per rep, entered rest between sets, 90 seconds per missing between-set interval, and 60 seconds between exercises. Round for display and store unrounded seconds. Exclude skipped sets and rest after the final set. Treat an empty draft as having no duration. Test edits, zero rest, missing rest, and midnight crossings. These defaults are product assumptions and should live in one place.

## 3. Implement `StrengthAdaptationsScreen`

- Model the layout after `src/screens/conditioning/ConditioningAdaptationsScreen.tsx`. The summary button pushes a full screen showing four independent bars and the evidence for each. Use **purple for hypertrophy**, **red for power**, **blue for strength**, and **green for muscular endurance**. Use text labels as well as color.
- Write a pure, versioned estimator over work sets. Use exercise-specific relative load for strength when a credible same-lift reference exists, challenging work-set volume and optional effort for hypertrophy, explicit explosive intent or velocity evidence for power, and sustained high-rep work with observed rest or effort context for local muscular endurance. Add optional explosive intent to the editor so power can be estimated without a velocity device. Keep absent evidence unknown and exclude warm-ups and skipped sets. Keep duration defaults out of the adaptation inputs. Base these rules on the references in [[2026-11-15 Strength Planning Handoff]]. The four values are heuristic emphasis indexes that may overlap.
- Return score or evidence level per quality, coverage, rationale, model version, and primary quality. Require sufficient evidence and a clear lead to assign a primary quality. Use a neutral marker for ties, mixed workouts, or insufficient data. Document the scoring bands and tie rule in fixtures. The builder uses its current draft as a preview. The repository computes and stores the performed estimate from confirmed sets at commit. Logged detail displays the stored result.
- Apply the primary adaptation color when mapping a logged strength session to `MonthEvent.color` for the Strength tab. Use the same color in the adaptation screen's bars. Keep Home on the existing Strength category color. The shared monthly component already renders caller-supplied colors and needs no Strength-specific logic.
